在仓库根目录运行：

```sh
pnpm install
pnpm run typecheck
pnpm run test
pnpm run build
pnpm --dir docs run build
```

需要 Node.js 22 或以上。持久化、智能体顺序和浏览器界面修改不能只凭构建成功判断。

| 修改 | 最低附加验证 |
|---|---|
| 规范模型或世界格式 | 解析问题、往返样例、会话初始化、创作工具 |
| SQLite 架构 | 新数据库、旧版本迁移、快照/恢复、分支 |
| 记录协议 | JSON Schema、解析、原子应用、回读、记录员验证 |
| 回忆 | 角色隔离、无向量降级、向量失效、故事时间遗忘 |
| 编排 | 协议顺序、重试、取消、稳定子智能体前缀、后台 settle |
| DSH 集成 | 契约测试、热重载、聊天重开、归档/删除 |
| 浏览器界面 | 类型检查、生产构建、专用 profile 中实测 |
| 文档 | 中英文生产构建，断链视为错误 |

核心包的 `tests/support/architecture.spec.ts` 和状态包的 `tests/architecture.spec.ts` 读取源码中的导入，分层被破坏时失败：共享代码只导入自身和模型；浏览器端不导入宿主代码、Node 或状态包；宿主不导入浏览器端；包只通过根导出使用；SQLite 只经由驱动访问；工具、记录和记忆看不到驱动；模型包只导入自身。需要新规则时加在这里，而不是只在文字里描述。

两个横切测试守住单个功能测试注意不到的问题。`tests/host/prompts/rules-coverage.spec.ts` 对每一条某类提示必须携带的规则（只根据所给内容工作；用该聊天提示所指定的语言书写），在每种随包语言里列出携带它的提示，以及（附理由）每一个不必携带的提示；之后新增的提示不在任何一个清单里，测试会失败，直到有人作出决定。一个回合循环测试读取发给角色的每一次请求，出现键、或回合/轮次编号就失败：故事里只有名字和时间，编号属于代码。

智能体循环测试使用确定性的 fake，断言工具调用和状态变化，不断言模型文风。并发测试应主动制造重叠并验证串行化、取消和清理。失败测试应证明操作已回滚，或留下明确可恢复的状态。

脚本化模型测试看不出真实模型如何处理提示词。`eval/` 会把若干场景（环顾四周并交谈、穿过出口、尝试世界规则禁止的事、等待数小时、说出角色必须记住的话）发送到正在运行的开发版 DSH，用你要评估的模型运行，再检查故事数据库、对话日志和助手记录。请使用临时的角色扮演根目录，不要用自己的：`node eval/run.mjs "<带令牌的 dsh 地址>" --label qwen-35b`。由模型扮演玩家的场景（`soak`：它用自己的话在几个回合里追求一个目标，故事必须保持完好）需要一个玩家用的模型（任何 OpenAI 兼容端点），没有时会被跳过：`node eval/run.mjs "<带令牌的 dsh 地址>" --only soak --player-model <名称> [--player-url http://localhost:8081/v1] [--player-key-env 环境变量] [--player-reasoning none|omit|low|high]`。玩家在各方面都有上限：最多 `--player-turns` 个回合（默认 6，绝不超过 30）、玩家自己的模型最多花 `--player-tokens` 个令牌（默认 30000）、最多 `--player-minutes` 分钟的墙钟时间（默认 40，并且不会开始一个按典型回合耗时会超时的回合）；一次回复最多 160 个令牌，一个行动最多 300 个字符；它只收到最近一段叙述和自己最近五个行动，而不是整个故事。当它说完成、重复自己、两次没有内容可读、写出不是行动的东西（以 `/` 开头的命令），或回合失败、结束时没有交付任何内容时，它会停下，报告会写明原因（`stop`：`done`、`turns`、`tokens`、`time`、`stuck`、`invalid`、`failed`）。`eval/player.test.mjs` 用桩服务测试这些上限（`node --test eval/player.test.mjs`）。报告写入 `eval/results/<label>.json`；加上 `--baseline eval/results/<之前的>.json` 时，会指出哪些场景变慢超过一倍、哪些检查此前通过现在失败，并以非零状态退出。场景是 `eval/scenarios/` 中的小文件，在线会话发现问题时就添加一个。

故事结束后还可以只读地事后审计：`node eval/audit.mjs <会话文件夹> --url <OpenAI 兼容地址> --model <名称> [--scope story|character:<名字>|turn:<n>] [--out report.json]`。评审模型阅读故事的记录（角色范围只看它参与或感知过的），并按 `eval/audit-criteria.json` 列出的错误（矛盾、捏造、时间线、知识泄漏、记忆遗漏、人设漂移、替玩家说话、重复）指出问题，每条都要指明所依据的记录。每个维度从 100 分起，由脚本而不是模型扣除每个有效错误的分值；没有记录编号或不在清单上的错误不计，记录不足以评判某个维度时评审弃权，分数为 `null`。标准只列错误、不给范文，是可编辑的文件；不给叙事质量打分。`eval/audit.test.mjs` 用桩服务测试评分与证据。

发布后不要修改旧 migration；新增有序迁移并测试升级。打开落后于最新架构的会话时，会先做完整性检查，并把升级前的数据库复制到数据库旁的 `migration-backups/schema-<版本>.sqlite`；若迁移损坏了数据，可把该副本放回为 `session.sqlite`。发布前检查构建产物没有私有包悬空导入，bundle 依赖及 patch 完整，包包含提示词/客户端/公开入口，中英文提示词模板及变量一致，可选 AI 能力逐项缺失时仍可运行，配置已纳入 Schemastery，并更新两种语言文档。

只在专用开发 profile 和可丢弃的世界/会话中验证，不能修改用户的普通 DSH profile。

## 质量门禁

拉取请求和推送到 `main` 时依次运行类型检查、带覆盖率的测试、发布构建和发布检查，随后进行 SonarQube 分析，其质量门禁必须通过；发布要等两者都完成。在本地生成同样的覆盖率：

```sh
pnpm test:coverage
```

每个包写出 `packages/<name>/coverage/lcov.info`，`scripts/merge-coverage.mjs` 把它们合并为 `coverage/lcov.info`，路径相对仓库根目录，也就是 `sonar-project.properties` 读取的文件。包内每个源文件都会列出，没有测试加载的文件按未覆盖计算，而不是缺失。测试、构建产物、示例世界、自带界面包和配置文件不参与分析或覆盖率统计。扫描需要仓库机密 `SONAR_TOKEN`，来自复刻仓库的拉取请求不会运行。请修复门禁报告的问题，而不是排除文件；只有测试无法运行的代码才可以添加排除，并在拉取请求中说明原因。

## 检查基准

世界检查有一套带标注的基准，位于 `packages/dsh-agentic-roleplay-core/tests/benchmark/`。它以虚构的港口小镇*盐湾港*为底本，中英文两个版本结构完全相同，并用到了世界格式的每一部分：有设定、声音、情绪、目标、关系、认知和日程的角色；带细节和各种状态的通路以及一把锁的地点；各种物品（隐藏的、上锁的、穿戴的、放在容器里的）；有成员和目标的组织；两种范围、带日期和关联的背景；各种类型和对象的跟踪数值；主要条件与效果类型的触发器；骰子、剧情线、日历、规则、提示词和开场白。每个用例都是在底本上植入一个缺陷（或没有缺陷，或一对看似重复实则不是的内容），并写明检查必须给出的发现，除此之外不得有别的发现。

- **每次都会运行**（`pnpm test`）：`coverage.spec.ts` 用两种语言的底本各开始一个故事，并按功能断言世界的每一部分都进入了故事，哪一部分不再进入就会点名。`cases.spec.ts` 运行由程序判定的用例（一致性、质量、首场景和与角色卡对照的检查），两种语言各一遍，并断言精确的发现。
- **在线运行**：使用开发机上的模型，统计精确率、召回率、误报、重试、回退和耗时。`BENCH_LIVE=1 BENCH_LABEL=<名称> BENCH_MODE=llm|decision|hybrid npx vitest run tests/benchmark/live.spec.ts` 会运行需要模型判断的用例（数值和名称在含义层面的重复、相互矛盾的背景、设定单薄的角色、平淡的开场、缺口，以及与角色卡的对照，其中包括不应被标出的改写和翻译）。结果写入 `eval/results/checks-<名称>.json`。`BENCH_ONLY`、`BENCH_LANGS` 和 `BENCH_REPEAT` 可缩小范围或重复运行；比较差异之前请把同一用例多跑几遍，因为模型每次回答都有随机性。
- **被追踪的数值**：`tests/benchmark/variable-cases.ts` 收录了一个小故事的 23 个带标注的回合（两种语言；数值有数字、开关和选项三类；既有同时改变多个数值、涉及多个人的回合，也有只是提到、回忆、担心或发生在别人身上、因而什么都不该改变的回合），`variables-harness.ts` 在预设的起始数值上对每个回合运行产品的追踪器。`variables-cases.spec.ts` 始终运行，用一个知道答案的模型检查这些用例。在线运行：`BENCH_LIVE=1 BENCH_LABEL=<名称> BENCH_MODE=llm|decision|hybrid npx vitest run tests/benchmark/variables.spec.ts`，结果写入 `eval/results/variables-<名称>.json`，包含哪些数值发生变化的精确率和召回率、新值正确的比例、被拒绝的编辑，以及按数值类型的分项。用例没有要求、但说得通的变化单独计数（`tolerated`）。`BENCH_TRACE=1` 会保留每个模型被问了什么、答了什么，包括决策模型给出的概率。
- **图片复用**：`reuse-cases.ts` 收录了 12 个时刻（两种语言），每个时刻有两到四张按字面相近而被选出的已存图片（表现该时刻的那一张，如果有的话，以及相近但不对的：另一个钟点、另一些人、同一地点的另一种状态）。`BENCH_LIVE=1 BENCH_LABEL=<名称> BENCH_THRESHOLD=<阈值> npx vitest run tests/benchmark/reuse.spec.ts` 用随附的问题把它们交给决策模型，统计选中数、首选错误（产品会展示第一张被接受的图片）和漏选。
- **状态面板**：`panel-cards.ts` 里是用中英文各编写的虚构角色卡，它们像社区卡片那样携带状态：围栏代码块里的一行数值、一块标记代码、卡片自创标签嵌套成的版式（标签名用卡片的语言，带填空占位符、联系人消息块、选项、绘制它的脚本，以及另一条讲这些消息怎么写的条目），还有状态追踪框架（初始值和更新块）。其中没有任何内容取自真实卡片。`panels-cases.spec.ts` 在常规测试中运行，用自带的判定器给确定性的部分打分：开场白和生成实体所用的片段里没有面板，面板交给了变量任务，要求打印的条目被清理，模仿开场白的游戏主持人先被退回、再被裁掉，而故事和台词保持不变。`BENCH_LIVE=1 BENCH_LABEL=<名称> npx vitest run tests/benchmark/panels.spec.ts` 用真实模型让每张卡经过调查、构建和完成，只要世界里出现状态栏、标签块、占位符、更新调用或要求打印的句子、出现 `quality-panels` 的发现，或一个变量都没有，就判为失败（与卡片显示数量的差距记在汇总里）；结果写入 `eval/results/panels-<label>.json`。`cases.ts` 中有中英文的 `quality-panels` 缺陷用例。
- **框架（数据驱动）**：`tests/benchmark/framework/` 运行的一切内容都读自 `tests/benchmark/data` 下的文件：基础世界（`worlds/<id>/<语言>/world`，即产品格式的世界文件夹，另有记录主题和语言的 `bench.json`）、层（`layers/<id>.json`：`requires`、`conflicts`、`fits`，以及 `remove`/`add`/`patch` 操作，补丁为 RFC 7386 合并补丁）、行（`rows/*.json`：世界、语言、层、角色阵容、组合后的世界必须具备的特性、用途，以及可选的脚本和探测）和 `excluded.json`（有意排除的组合及原因）。`data.spec.ts` 会在以下情况失败：未知的层、缺少依赖或存在冲突、超出主题且未声明为探测的层、关于特性或阵容大小的声明与组合后的世界不符，或组合后的世界通不过程序自身的检查；它的覆盖报告列出出现在不足两个主题或只有一种语言里的特性，以及某个主题缺少的阵容档位。增加世界、层或行无需改代码。盐湾港是第一个基础世界：每种语言有完整行、单角色行（故事里只有一个可被询问的角色）和小阵容行（三个），由删去角色及所有相关引用的层构成。`rows.spec.ts` 把每一行作为真实故事启动，检查谁在扮演、故事可以询问多少其他角色，以及声明的特性都进入了故事、没有声明的特性都没有进入。行可以指定一份脚本（`data/scripts/<id>.json`）：用聊天所用语言写成的玩家回合，每个回合带有来自封闭列表的预期；一个步骤也可以重新生成上一回合，或把故事退回到更早的回合（`/ooc`、`/wait`、`/roll` 按玩家的写法直接写）。针对某一回合的叙述：没有面板、语言正确、含有或不含某段文字、某个角色开口、玩家角色没有被替说话。针对整个故事：回合数、某个角色存在且有位置、玩家能读到的某个被追踪数值发生了变化或显示某段文字、某个触发器已触发、某个角色站在某处、某个角色持有某件东西、世界作者编出了新的人物、没有哪句话被重复送出。运行中无法观察的预期记为“未判定”，绝不算作成立。一个步骤也可以等待若干分钟真实时间、期间没人发言，用于在玩家不在时继续进行的故事。还有更多预期会读取：角色留下的消息、开场白、故事设置、正在使用的界面包以及某个文件夹里的文件。行可以给故事若干文件夹供文件工具使用（脚本用 `{workspace}`、`{folder:<名称>}` 和 `{outside}` 指代），也可以给出开始对话框对世界的开局问题的回答。结果按语言和主题分别汇报每一类预期，从不平均，并列出在一些重复里成立而在另一些重复里失败的预期。行还可以带聊天设置（例如用来测试用另一种语言讲述的世界、真实时钟或输出把关）和一处有意植入的缺陷：加入一份要求状态栏或泄露世界秘密的风格提示层，并要求程序自己的检查标出这个世界。它的结果单独报告为“抓到”或“被挡住”，不计入得分。另外还有按使用场景设计的世界：一个用真实文件工具在临时文件夹里搭网页的助手（按它留下的文件打分）、取材于公版作品的陪伴式故事（写法上让角色所知的一切来自世界、而不是模型对原著的记忆），以及一个人群要由故事自己编出来的集市。按题材划分的基础世界有五个：盐湾港（悬疑，英文及其中文译本）、巷口面馆（日常，用中文写成）、灰烬之路（奇幻，用英文写成）、青石镇（武侠奇幻，用中文写成）和彭伯顿面包店（日常，用英文写成），因此除悬疑外，每个主题都有两种语言的世界。`BENCH_LIVE=1 BENCH_URL=<带令牌的 DSH 地址> BENCH_ROOT=<临时根目录> npx vitest run tests/benchmark/rows-live.spec.ts` 针对运行中的 DSH 把带脚本的行作为真实故事来玩（`BENCH_ROWS` 选择行，`BENCH_REPEAT` 重复），为每次运行写一份追踪，并把游戏主持人的聊天日志放在旁边，同时为故事启动的每个辅助智能体（角色、记录员、作者、建议者）写一条 `helper` 事件：它的指令、简报、每一步和每次调用、结束的方式，以及结束不佳或从未交回结果时的问题（原始日志保存在追踪旁边的文件夹里），按行和语言分列的得分写入 `eval/results/rows-<label>.json`。
- **追踪**：每个在线基准用例运行时都会写一份追踪（`<输出目录>/traces/<标签>/<语言>-<用例>-<序号>.jsonl`，每行一个 JSON 事件），因此无法重现的失败第一次出现时就已留在磁盘上。其中有所用的模型和采样、完整发出的每个请求（从不含密钥）、每个原始回答及耗时、任务自身检查退回的回答及原因、任务接受的回答、评分器所读状态的命名快照（卡片、分类、提取出的实体、世界的文本、数值追踪用例的设置和追踪器报告），以及每条预期一项记录，写明是否成立和发现了什么。`BENCH_TRACE=0` 关闭，`BENCH_TRACE_DIR` 指定位置。已记录的运行可以在没有模型的情况下重新评分：`BENCH_REPLAY_DIR=<文件夹> npx vitest run tests/benchmark/panels-replay.spec.ts` 让每次记录下来的面板导入由录像代替模型作答，并要求结论与在线运行一致，这也说明判定器和导入器仍能抓到当初抓到的问题。`trace.spec.ts` 用桩模型检查写入、密钥不外泄、完整性检查和重放。
- **Langfuse 中的追踪**：AI 提供方插件的可观测性开启后（在设置中，或在它的补丁行里设置 `traceEnabled`、`traceSink` 和 `langfuseHost`），在线运行中的模型、回合和辅助智能体也会记录为嵌套的追踪；设置 `BENCH_LANGFUSE_HOST`、`BENCH_LANGFUSE_PUBLIC_KEY` 和 `BENCH_LANGFUSE_SECRET_KEY` 后，每个行的判定会作为评分（`bench.row`、`bench.<种类>`）写到故事的会话上，这样一个失败的预期就能和导致它的请求放在一起看。密钥放在环境变量或凭据存储里，不要写进仓库中的文件。
- **语气评判**：`BENCH_LIVE=1 npx vitest run tests/benchmark/voice.spec.ts` 把每种语言的 24 句台词（6 个设定了说话风格的虚构角色，既有符合风格的句子，也有在用词、语气或做派上违背风格的句子）逐句交给决策模型回答是或否，并与标注比对（`BENCH_DECISION_URL`、`BENCH_DECISION_MODEL`、`BENCH_THRESHOLD`）。脚本里的 `speaks-in-voice` 期望用同一个问题评判角色在故事里说过的台词：实时跑行时需要 `BENCH_DECISION_URL`，没有它就不评判。Kev-9B 在 0.5 的截断下把 96 句（两次运行）全部分开；违背风格的句子很明显，所以结果只说明评判可用，不说明它能看出细微的偏差。
- **重排序试验**：`BENCH_LIVE=1 npx vitest run tests/benchmark/rerank.spec.ts` 对三组带标注的数据（数值、事物、背景）里的每一对，分别按嵌入相近度和重排序模型排序，并统计真正的重复对有多少落进检查会交给模型询问的那十二对里。
