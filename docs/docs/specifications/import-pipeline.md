---
title: Character-card import specification
description: Staging, resumable phases, classification, image security, approval, and validation.
---

A SillyTavern character card (PNG with an embedded `ccv3` or `chara` chunk, or its JSON; spec V2 and V3, V2 is normalised to V3 first) becomes a new world. The importer writes native world files; if the result cannot start a story yet, it remains visible as a repairable draft rather than losing the work.

## Flow

1. **Upload** (Worlds page, *Import*). The host reads the card (`host/import/card.ts`, at most `importMaxUploadBytes`, 100 MB by default), keeps it in a temporary import folder and shows what it holds.
2. **Choose** what the importer is told: the world's name, which lorebook entries are switched off (they are not passed on), and which one opening is used (the first message or one alternate greeting).
3. **Start.** A world is created, the upload is moved into its `.import/` folder, its authoring chat is created and the plugin sends the message `/import-st .import/card.json …` for the person. The authoring agent recognises the command (`agent/pre-step`), is told the procedure instead of an ordinary request and may not end the turn before the import is done.
4. The three tools of the import, each doing its work in narrow agents of their own (`runChild`, one small job per call, several at once up to `importConcurrency`):
   - `import_survey`: **itemise** every piece of the card (fields, the opening, lorebook entries, long ones cut at paragraph or sentence ends), have each piece **classified** (what it is: character, player, speech, place, faction, thing, world, scenario, instruction, generator, template, irrelevant, and which named things it is about), and **merge the names into a roster** of characters, places, factions and things (a model call, with a deterministic fallback that folds names contained in others).
   - `import_build`: **extract** one document per entity from the pieces that are about it, and the background pieces as lore entries. Documents are checked with the same parsers the world uses, and refused with the reasons until they are valid.
   - `import_finish` (then a review): stage everything, write the native files with the description, tags, opening message and cover picture, and check the **whole world** with the same validation a session start uses. The same turn then **reviews** the world like a careful editor with the authoring tools (places and their ways, starting places, duplicates) and corrects what the narrow jobs could not see without asking for each edit (`reviewing` in `.import/state.json` lifts the approval gate until that turn ends). If problems remain, the files stay as a draft and the assistant continues repairing them.
5. The phases are kept in `.import/state.json` (`ready`, `surveyed`, `built`, `repair`, `done`), so an interrupted import resumes where it was and each step refuses to run out of order.

The narrow jobs use the plugin-wide **Imports and authoring assistants** settings. They can use a separate model and reasoning level from the authoring chat, run with bounded concurrency, and stop after `importTimeoutMinutes` rather than holding an import indefinitely. `importMaxTokens` is a ceiling: classification, roster, entity, lore, style and translation jobs each request only the smaller budget their result needs. If a helper fills that budget with prose instead of calling its result tool, the run stops immediately; retrying the same truncated answer would spend the same budget again. `import_build` may run only twice in one authoring turn, which prevents a model from repeatedly rebuilding an import that is not converging.

## Decisions

- Where an entry is in the card, or whether it is constant or keyed, says little about what it is: cards use lorebooks as world background, as reminders for one character, or as the whole definition. Every piece is therefore judged by its content, and the lorebook is never imported as it is.
- When `importDecisions` is `decision`, the configured decision service first checks whether a piece is only an AI instruction or irrelevant reader-facing material. A result at or above `importConfidence` is accepted without a language-model classification. Uncertain answers and decision-service failures fall back to the language model, and the survey reports both how many pieces were settled and any fallback problem. The decision model is never trusted alone for a piece that may describe the story.
- **Tracked values are read in groups** (`extractVariables`). The tracking text of a card (panels, formats, state specifications) is cut into groups of at most 6 000 characters and each group is asked on its own; each request declares at most `importVariablesPerRequest` values (default 25) and is asked again, told which keys are declared already, while it fills its share; the first declaration of a key stands, and a world has no limit on how many it tracks. A declaration that cannot be used (a choice with one option, bands that do not rise) is left out with its reason and does not cost the rest of the answer; a constrained reply that ran into the output limit in the middle of a long list is closed after its last whole entry, and the next round asks for the rest. One request holding all of it made the model write on until its limit without answering (found live on a card with long variable rules), which lost every variable. Helper requests may write up to `importMaxTokens`; its default, 0, is a tenth of the model's context window (at least 16 000), and each job adds room for the analysis the model tends to write first.
- **Casting as machinery** (`host/import/casting.ts`, prompt `import/casting`). The casting passages found above are read once more, as a whole, and become the world's own mechanics: `commands.json` (the slash words the card names) and `triggers.json` entries whose effect is a beat that has the world author make the person (`dispatch: author`, `need`, a drawn option from the card's list in `draw`). A trigger starts from a command's flag, or from a statement about an event in the past tense that a model judges (`decisions.triggers` chooses who judges). A mechanism with nothing to start it is left out with a note, and a command no trigger uses is not kept.
- **Checks while editing, and the import record.** Every authoring write (elements, relationships, plots, triggers, world info) returns, next to its result, what the whole world still needs before a story could start (`world_check` in the result: `ok`, or up to eight open problems and how many more); it is advice, because a half-made world is a normal state in between. `.import/provenance.json` (`schema: dsh-roleplay-import/v1`) keeps one line per import or update: time, card name, a SHA-256 of the card as read, language and, for an import, the counts and the number of notes; a file of another schema is refused, never rewritten.
- **Standing rules and casting guidance** (`extractEntities`, prompt `import/generator`). Every substantive piece is asked one question with two lists, each passage copied word for word and checked against the piece: *casting* (how people, places or things are made up in play) and *rules* (standing rules and mechanics the game master applies: checks, combat procedure, tables, how state is tracked). Casting becomes game-master-only lore ("how people are made up"). Rules from a lorebook entry the card always sends (`constant`) are joined into the world's prompt `roleplay/standing` (at most 12 000 characters, `${` and `{{` made inert), which the game master prompt carries on every turn; everything else, and what does not fit, becomes game-master-only lore ("rules and mechanics"). Before classification the classifier is shown the outline of the whole card and contrasting examples, a name that holds the player marker is taken as that name with the player's word instead of being refused, EJS control code is taken out of every piece (its branches stay as plain text), pieces that name a variable-update tool (`stat_data`, `[mvu_`, `<UpdateVariable>`, JSON Patch) always reach the variables job, and a name that only turns up once inside pieces about others does not become an entity.
- **Drafts and repair** (`host/import/draft.ts`, `run-import.ts`, `worlds/world-check.ts`). `import_finish` mends what code can settle (dangling faction members, relationships, known places, parents, ways and starting places are dropped with a note) and writes the world even when `checkWorld` (the validation a session start runs) still finds problems: the import state becomes `repair`, the result carries `draft`, `WorldSummary.draft` marks the card. The assistant is told to repair with `world_check` and the card; when a turn that could change the world stops while it still would not start, the import hooks send it back (`import/repair-again`, at most 5 times); `endReview` leaves the state at `repair` if problems remain and `settleDraft` makes the world ordinary once `checkWorld` passes. `GET /worlds/import/draft?id=` gives the status and problems; `POST` with `action` `ask` (the import command is sent again and the turn runs with the approval gate lifted, `startRepair`), `keep` (`keepDraft`) or `discard` (the folder goes to `<root>/.trash/worlds`). Files are written with `atomicWrite` (`host/atomic-write.ts`) and `world.json` changes go through `updateWorldFile`, which serialises them per world.
- **Carrying on.** An import that stopped (a server restart, a refused finish, a chat that ended early) keeps the card and what was extracted in `.import/`; `POST /roleplay-api/worlds/import/resume?id=<world id>` sends the import command to the world's chat again and the import hooks continue from the phase the import reached (422 when no import is waiting).
- **Guidance on making people up** (role `generator`: pools of kinds and situations, templates, tables, the fields a profile must have, when to bring someone in). It is kept word for word as lore of kind `custom` and scope `listed` (the game master and the world author read it, characters do not), never rewritten by the lore job and never made into entities (`isGeneratorOnly` pieces give no names to the roster; a piece that mixes it with other content keeps both). In play the game master prompt says to read it when a scene could bring someone new and to call `expand_world`; the world author's prompt says to search the lore for it and follow it. A card with no cast imports as a world with no characters, which is started by bringing an avatar.
- Instructions to the AI are **partly** carried. `import_build` has one narrow job (`import/style`) read the card's system prompt, its post-history instructions and the pieces judged to be instructions, and keep only guidance on how the story is written and how the characters behave (voice, tone, perspective, staying in character, how a character declines). That becomes the world's prose prompts `roleplay/style` and `roleplay/character-style` (`Extracted.prompts`), written by `import_finish` into `prompts/<language>/roleplay/` for every shipped language, because the card's wording does not depend on the interface language. Rules of the game, formats, status panels, scripts and anything about specific entities are not carried; what the job named as left out is a note in the report. A text that is too long or uses a placeholder the prompt is not given is refused and the instructions are then not carried (a note says why); the import goes on.
- **Pictures the card points to** (`host/import/pictures.ts`). Every string of the card, scripts and extensions included, is scanned for web addresses (`NormalizedCard.urls`). Those that name a PNG, JPEG, WebP or GIF file, or have no file type at all, are fetched in the background from the first import step on (`pictures.json` in the import folder; `import_finish` waits for the run) into the world's `images/library/` as if the person had uploaded them: reusable, undescribed until a session's interpreter reads them, copied into every session started from the world. A failure here never stops an import. Safety: only http/https on ports 80 and 443 without credentials; a literal private address is refused; names are resolved at connection time and refused when any answer is loopback, private, link-local, shared, multicast, reserved or an IPv6 form that embeds one; every redirect (at most four) is vetted again; no proxy. A HEAD request first drops what answers 404/410 or declares a non-image type; a service that refuses HEAD or declares nothing is fetched anyway. The download has a size cap (20 MB) and a timeout, ignores the declared type and keeps a file only when its first bytes are an image of a supported format and it is not tiny (1 KB) or a copy of another picture of the card or of one already in the library (compared by `pictureHash`: the pixels' PNG chunks without text, time and EXIF chunks, so the metadata written into saved files does not hide a copy). There is no limit on how many addresses are tried (cards can hold thousands); eight run at a time.
- **Tracked values.** `import_build` has one narrow job (`import/variables`) read the card's panels and formats (pieces judged to be templates) and its instructions, and declare what the card keeps track of (numbers with limits and bands, flags, choices; feelings are never declared, they exist already) as the world's `variables.json`. Declarations are checked as the world checks them (`variableProblems`) and refused with the reasons until valid; keys are lowercase ASCII with underscores, and the names of characters, places and things it is limited to are turned into their keys. Initial values per entity are not extracted: a default applies. A failure is a note, never a stop.
- **What characters know of each other and the world.** A character's `knows` (places, things and ways between two places from the roster) becomes `knowledge` in its file (`locations`, `items`, `exits`), pruned to what was written and to ways the places really have (`pruneKnowledge`); the lore entries about a character are added to what that character knows, and a character named in someone's relationships gets a plain `acquaintance` relationship back when it has none (`completeAwareness`), because in a closed world a missing edge means not knowing the other exists.
- **Narration presets.** A SillyTavern prompt preset can be applied to an existing world: the Worlds page's **Import narration preset** uploads it to `<world>/.import/preset.json` (`POST /worlds/import/preset`), the world's authoring chat is asked to call `import_preset`, and the same `import/style` job turns the enabled prompts, in the preset's order (`readPreset` reads both the prompt-list layout and the older fixed keys), into the world's prose prompts. The call asks the person first because it replaces the world's own versions. The same job also fills a library preset: see Presets in the prompt system specification (`import_narration_preset`, `POST /presets/import`).  Ticking **Without the assistant** in the dialog skips the conversion: no model runs and no question is asked, the ticked prompts become the world's narration style (`roleplay/style`) word for word in every shipped language, and the preset's sampling is written to the world. A style the world already carries is first moved to the world's `.trash`.
- **Lorebooks.** A SillyTavern lorebook (an export with `entries`, or a card's `character_book`) is imported into the lorebook library, not into a world: `POST /roleplay-api/lorebooks/import?name=&language=` reserves an empty library entry, keeps the file in its `.import/lorebook.json`, opens the lorebook's authoring chat and tells it to call `import_lorebook`. Entries that are off or empty are dropped and the tool's macros replaced. A narrow job (`import/lorebook`) decides for batches of at most eight entries (within a text budget) what each is: *knowledge* (kept **word for word**; the model gives a title, a kind, a one-sentence summary, and a scope with `known_by` only when the entry clearly states who knows it, otherwise `everyone`), *steering* (an instruction to the AI, rewritten as short guidance for a target prompt: style, character-style, persona, game-master or character-rules) or *skip*. Every entry must be decided or the answer is refused; the import fails as a whole when a batch never gives a usable answer, so nothing half-made is written. Knowledge becomes entries of the book (the entry's keywords go into its summary); steering is kept in `.import/steering.json`. `apply_steering` then makes a new library preset in which each target prompt keeps its shipped text and the guidance follows it, in every shipped language; it asks the person first, with a warning when a target is not a prose prompt. A catalogue entry of type `sillytavern/lorebook` takes the same path (`POST /roleplay-api/catalogue/convert/lorebook`).
- **Other greetings.** The card's other greetings (the first message, and the alternates that were not chosen as the opening) become the world's `alternate_openings`, which the start dialog offers; the player marker and the card's markup are cleaned as for the chosen opening.
- **Portrait.** The card's picture is also the canonical reference portrait of the character that carries the card's name (or the only character), written with metadata as an image the person brought.
- There is no player character unless the card supplies one. A world without a playable character shows a warning in the editor and cannot be started until one is added.
- The player in the card's text (`{{user}}`) is the marker `[PLAYER]` for the models and is replaced by the player's character or a plain word at the end. `{{char}}` is the card's own name.
- Ids are made from names in any script. Folder names, ids and image paths accept the letters and digits of every language, never separators or dot segments.
- Several characters in one card are supported: the roster decides who they are.
- Cards are the property of their authors: tests use invented cards (`tests/support/cards.ts`), never content of a real one.
- **The card stays.** `.import/` is not removed after an import, and the authoring chat of the world has read-only tools over it: `card_overview` (every field, greeting and lorebook entry with its size, what the survey took it to be and which entities it was made into, the roster and the report's notes), `card_search` (phrase, then word, matches in any script, snippets), `card_read` (one piece word for word, 6000 characters a turn) and `card_origin` (the pieces an entity was built from, recomputed with the same `sourcesFor` the build used; for a name the import made nothing of, the pieces that mention it). They exist while `.import/card.json` does, so deleting the folder turns them off. The procedure prompt tells the assistant to look the card up, to treat the world's files as canon and the card as evidence, and to check the import's records against the text. The card is not shared by anything the plugin exports or translates (translation skips `.import`; there is no other export); sync carries it with the world. Play never reaches it.
- **Updating a world from a newer card** (`host/import/update.ts`, `update-tools.ts`, `card-diff.ts`, `snapshot.ts`). Reviewing a card (`ImportPreview.targets`, from `findTargets`) lists every world whose `.import/card.json` exists with a finished import, those whose name equals the card's first (`sameName`); `edited` compares the world's files with `.import/files.json`, a SHA-256 snapshot written when the import turn ends (`endReview`; `images/` and top-level dot entries excluded), `unknown` when there is none. A world's own page offers the update through the same review (`GET /worlds/import/update?id=` says whether the world was made from a card, whether an update waits and whether the last one can be undone). `POST /worlds/import/start` and `/catalogue/convert/staged` take `update: <world id>`; `startUpdate` keeps the world's files (not `images/`, not dot entries) and the import's records in `.import/before-update/`, moves the upload into `.import/update/`, opens the authoring chat and sends `updateMessage`, a plain request with no special turn, so every edit is approved like any other (`authoringApproval` applies); `updateHooks` sends an update turn back once if it stops with the update still waiting (a model ended a live turn on a change it found no place for), and lets a second stop through so a question can end the turn. `card_diff` (read-only) pairs the pieces of the two cards (`matchPieces`: fields by id; entries by title and keys, then by text, then by number with half their words shared), diffs changed pieces by sentence (`diffText`, at most 1500 sentences), adds the entities each old piece was made into (`entitiesByPiece`, the import's records; for a dropped piece also the ones only it made, `madeOnlyFromIt`), names what the card changed about the world itself (`worldFieldChanges`: description, tags, author, opening, other openings) and the files edited since. The assistant carries those with `edit_world_info` (which changes the `world.json` fields of `WORLD_INFO_FIELDS`, asks like every other edit, and refuses the name, preset, lorebooks, sampling and tool switches) and removes what only a dropped piece made unless the person edited it. `card_read` and `card_search` take `version: new`. `card_update_finish` keeps the old card, choices and picture in `.import/previous`, writes the new ones, carries `classification.json` over to the new piece ids and forgets dropped pieces, fetches the picture addresses the old card did not have and those the saved `pictures.json` shows failed for a reason that may pass (`addressesToFetch`, `worthAskingAgain`; with no record, the old card's addresses count as settled), merges the answers into `pictures.json` (`mergeReports`), lists fetched pictures whose address the card dropped (`droppedFromTheCard`, kept in the library), replaces the portrait that is still the card's picture (reference image with origin `uploaded` and original name `picture.png`) by the new picture, and takes a new snapshot. `DELETE /worlds/import/update?id=` (`revertUpdate`) puts the kept files and records back, moving what the world holds to `.trash/update-<time>`. The editor's default is update for a same-name world with `edited: no` and a new world otherwise; the world keeps its name; a catalogue release records its new version as the world's origin.

## Prompts

All instructions of the import are files under `import/` (see the [prompt-system specification](./prompt-system)), in the language the person was using when they started it. Labels constructed by the host for the classifier and roster use that language too.

The review that follows an import may adjust those and also write the prose prompts of the world (`roleplay/persona`, `roleplay/style`, `roleplay/character-style`, documented in the [prompt system specification](./prompt-system)) when the card asks for a narration style or for how the characters behave; the other prompts are rules and are refused to it.
